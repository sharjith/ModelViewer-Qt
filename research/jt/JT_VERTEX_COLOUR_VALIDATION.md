# JT lossless vertex colours

19 October 2026, `feature/JT-importer`, after `cc626c3`. The owner reports that all supplied viewer tests passed. This pass remains uncommitted.

## Qualified path

The JT 10.0 triangle path now reads lossless RGB and RGBA component arrays. The reference layout is section 7.1.2.3 (topologically compressed vertex records) and section 13.1.6 (compressed vertex colour array). Colour arrays follow the normals and precede texture-coordinate/flag arrays. Binary floating-point words pass through the Lag1 predictor before reinterpretation as floats. The first four words follow the existing predictor's unpredicted-prefix convention.

The topology decoder's historically named normal-index output addresses the complete vertex attribute record. Coordinate/attribute-record pairs are therefore retained even when two corners have identical positions and identical numerical normals but different colours. Colour seams also work without stored normals. Counts, component widths, decoded values and corner indices are checked; long corner loops poll cancellation.

The scene builder copies colours into Assimp's first colour channel, retains them through canonical-geometry copies, and copies each corner's colour during flat-normal expansion. The existing generic loader and renderer consume that channel. The material's vertex-colour override data flag (`0x0020`) accumulates under field inhibit/final bit 4, with forced and ignored attributes respected. When it is enabled, the render variant drops the colour channel and uses the material colour. Otherwise a white diffuse multiplier prevents the inherited material colour from tinting the authored vertex colours. Geometry cached for another occurrence is not modified.

RGB and opaque RGBA are supported. With blending disabled, stored vertex alpha is inactive and is set to one for rendering. Active translucent vertex colours are rejected rather than passed into the viewer's opaque sorting path. Quantized RGB/HSV colours, palettes and texture fidelity remain outside this pass. Unsupported colour representations can fall back to another usable LOD. Failed imports now retain the final display/LOD rejection reason in the error text instead of losing it behind a generic failure.

Colour hashes are consumed but not verified, consistent with the existing coordinate/normal hash handling. The current result is a tested subset, not a complete JT colour implementation or independent conformance result.

## Source boundary and provenance

`JtDecode_VertexColors.hxx` is a new, original ModelViewer GPLv3 helper. The adapted upstream `JtElement_ShapeLOD_Vertex.cxx/.hxx` connect the stream and assemble coordinate/attribute pairs. Existing notices remain. `PROVENANCE.json` and `MODIFICATIONS.md` record the addition; 116 decoder files comprise 104 upstream-derived files and 12 original additions. The scene/material adaptation is original code in `src/Import/Jt`. No upstream contribution, additional dependency, proprietary implementation, new JT version or XT backend is introduced.

## Automated evidence

The isolated MSVC AddressSanitizer suite checks:

- Known RGB/RGBA values in both byte orders, including records beyond the four-word predictor prefix.
- Every truncation point in those packets, bad counts/components, unsupported quantization, and nonfinite/out-of-range values.
- Red/green corner seams with shared positions and identical normals; the same seam without stored normals; flat-normal expansion.
- Material override inheritance, final/inhibit/force/ignore, geometry-cache isolation, inactive vertex alpha, and explicit rejection of active translucent colours.
- Production scene copying and GLB export/reimport of the colour channel.
- All five original part regressions, retaining geometry, normals and opacity.

The local fixture generator additionally injects authored colour packets into all display LODs of a locally supplied Bolt, updates container lengths/offsets and bindings, and imports the resulting native files. It compares every selected position, normal and triangle index against the original. It checks uniform-blue material override, flat-normal colours and fallback from an unsupported colour alternative.

These fixtures are generated by our own serializer and decoded by our reader. They are regression checks, not an independent oracle. Their colour hash words are placeholders. Real independently authored coloured JT files and independent viewer comparison remain needed. Downloaded sample geometry and generated models remain in ignored `out`, not the repository.

## Reproduction and UI checks

Build the existing standalone `tests/jt` project. Run `jt_tests <sample-folder>` and:

```text
jt_color_fixturegen out/jt-research/samples/Bolt.jt out/jt-research/vertex-color-fixtures
```

After rebuilding ModelViewer, open the files in `out/jt-research/vertex-color-fixtures` in a shaded raster mode:

| File | Expected result |
| --- | --- |
| `vertex_rgb.jt` | Bolt with vivid red, green and blue patches by attribute-record order; 913 vertices, 904 triangles |
| `vertex_rgba_opaque.jt` | Same colours/counts, fully opaque |
| `vertex_override_blue.jt` | Uniformly blue Bolt, same geometry counts |
| `vertex_rgb_flat.jt` | Same patches with faceted normals; 2,712 vertices, 904 triangles |
| `vertex_quantized_unsupported.jt` | Error retaining the unsupported quantized-colour reason |
| `vertex_color_lod_fallback.jt` | One coloured Bolt loaded from the usable alternative, 913 vertices, 904 triangles |

Keep the files together: the flat and LOD-fallback assemblies reference adjacent files. Check the original Bolt still looks normal. Save/reopen the coloured result as MVF to check the application's full persistence path. The owner reports all supplied viewer tests passed; a separate MVF result was not itemized. The agent has not built the full application or independently compared a real authored coloured JT file.
