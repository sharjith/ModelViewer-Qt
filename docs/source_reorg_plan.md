# Source Tree Reorganisation - Proposal

Status: **PROPOSAL for decision** (2026-09-26). Nothing has been moved. The exact file-by-file mapping is `docs/source_reorg_mapping.csv`
(generated by rule; every one of the 520 source and header files is assigned).

## 1. Where we are

`src/` (237 files) and `include/` (281 files) are flat: 520 files, one namespace of file names, one include directory. Everything from the GL
layer to the Code_Aster reader sits next to each other, and the only subfolder is `src/cuda/` - which is not a feature folder but the three OptiX
`.cu` device files that need their own compiler step; the C++ host code that drives them (`RtOptix*.cpp`) is flat in `src/`.

What hurts: finding things (a person must know the class name), no visible module boundaries or dependency direction, tests that must list their
sources by hand, 35 undo commands mixed with everything else, and three monoliths (`ViewportWidget.cpp` 19,977 lines, `ModelViewer.cpp` 8,081,
`SceneMesh.cpp` 4,877). What is good: the build is one glob and everything includes headers as `"Foo.h"`.

## 2. Proposed tree

Dependencies point down the list (a module may use the ones above it, never below). Feature modules sit beside each other and use the layers above them.

Notes on the choices:

- **Commands go with their feature** where they belong to one (a measurement command lives in `Measurement/`, a material command in `Materials/`,
  shrink wrap in `MeshTools/`); only the generic scene-editing commands stay in `Commands/`. A feature is then one folder to read, test and own.
- **Layers vs features.** The lower layers (Core, Geometry, Render, Scene, Viewport) follow the existing class hierarchy
  (`MeshGeometry -> RenderableMesh -> SceneMesh`); the feature modules are what is added on top and are the natural unit for the later CMake
  library split.
- **Split of the monoliths is a separate track** (e.g. `Viewport/ViewportWidgetSelection.cpp`, `...Clipping.cpp`): moving files and splitting files
  should never be one change.

## 3. Decisions needed

| # | Question | Recommendation |
|---|---|---|
| D1 | Headers next to their sources, or a mirrored `include/`? | **DECIDED (user): keep `src/` and `include/` as top-level folders, with the same module subfolders in each** (`src/Render/Foo.cpp`, `include/Render/Foo.h`). The Simulation move follows this. |

| D4 | Commands | Split by feature as above. |
| D5 | Enforce the layering | Later, with CMake targets (see phase 7): a module that includes something below it fails to build. |
| D6 | Folder name `Simulation/` and the sub-split `Readers / Core / UI` | Yes: it is also the shape for a `SimulationCore` library (Core + Readers, GUI-free) that the tests link. |

## 4. Mechanics

- **A script, not hand edits.** One `git mv` per row of the mapping file, run per phase, so the result is deterministic and reviewable; `git log --follow`
  and `git blame` keep working through renames.
- **CMake:** the two globs (`src/*.cpp include/*.h`, `ui/*.ui`) become `GLOB_RECURSE ... CONFIGURE_DEPENDS`; the include directories are collected from
  `include/` (every folder that has a header); `add_optix_kernel(... src/cuda/*.cu ...)` gets its new path; AUTOMOC keeps working because the
  `Q_OBJECT` headers stay in the glob. `tests/CMakeLists.txt` lists its sources explicitly and is updated per phase.
- **Other references to fix:** `.ts` files (paths inside; `lupdate` regenerates them - the end-of-list translation step is the best moment), `docs/*.md` path mentions
  (sed), `ModelViewer.qrc`/packaging if they name source paths (they do not for `src/`).
- **Order (each phase is one commit that you build before the next):**
  1. ThirdParty + Simulation (the pilot; the Simulation part is already agreed).
  2. RayTracing (+ `cuda/`), Import, Mvf.
  3. Materials, Measurement, Analysis, MeshTools (their commands move with them).
  4. Commands, Scene, Viewport.
  5. Render, Geometry, Core, App (most-included headers last: with flat includes nothing changes for the includers, this is only for order of review).
  6. Cleanup: `.ui` files grouped into `ui/<Module>/` (the `ui/` glob becomes recursive), docs and `.ts` paths.
  7. Optional: CMake static libraries per module (`SimulationCore` first), then qualified includes and enforced layering.

## 5. Risks

- **Other branches.** There are ~20 local branches (`feature/*`, `experimental/*`). Files moved unchanged are followed by git's rename detection in merges,
  but a branch that also edits a moved file will conflict more often. Merge or rebase the branches you still care about before phase 2, or plan to
  cherry-pick with `-X find-renames`. This is the main reason for D7.
- **I cannot build here.** A phase can fail only at configure, moc/uic or include-path level (never subtly): one build after each phase finds it, and the
  fix is a path. Keeping phases small is what makes that cheap.
- **Include-name collisions.** With flat includes plus many include directories, two headers with the same basename in different folders would clash; the
  mapping check found none (basenames are unique today) and the script refuses to create one.
- **Muscle memory / tooling.** Qt Creator and Visual Studio pick up the new layout from CMake; the `.user` file is untouched.

## 6. Recommendation

Do phase 1 (ThirdParty + Simulation) as soon as the current simulation work is tested and committed, review the result, then decide on the rest with
the pilot in hand. Accept D1-D4 as recommended; D5-D7 can wait. Total effort: the moves themselves are a script run; the cost is the phase-by-phase builds.
